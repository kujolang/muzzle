# Muzzle 1.1.2 release receipt

Date: 2026-10-12. Repository: `kujolang/muzzle`, branch `main`.

## Published release

- Previous official release: v1.1.0. There were 18 commits after it at the pre-release starting SHA `f377606c2c918c4688c0dd1b83db94f111bea394`.
- Preparation commit: `b3f7511d52989a29feeacba9cf58bbb082d62c88` (v1.1.1).
- Final release commit/tag: `fcfe9fdecdff088ca6a9f25928089ce9aada16ee`, [v1.1.2](https://github.com/kujolang/muzzle/releases/tag/v1.1.2).
- GitHub release ID: `410765953`. Source and Kennel package distribution; no standalone binary assets are claimed.

Version 1.1.1 was published before the real Kennel global-install test exposed a packaging defect: the manifest selected `muzzle.kujo` directly, bypassing the Bash wrapper and resolving helper paths against the caller's directory. A workflow then exited 127. Version 1.1.2 adds `[bin] muzzle = "muzzle"` while retaining the existing Kujo entry. The new regression fails against the immutable v1.1.1 source and passes against v1.1.2. The earlier release remains available, with a superseded notice and upgrade instructions; neither tag nor archive was rewritten.

The README was revised using the requested Orwell writing skill. It gives direct setup steps, describes the trusted-local boundary, removes unsupported token-saving examples, and retains command, manifest, runner, and compatibility guidance. Version markers in the wrapper, Kujo entry, manifest, specification, installer, installation regression, and current documentation agree on 1.1.2.

## Compatibility and migration

CLI arguments, JSON schemas, manifest formats, environment variables, and exit-code contracts remain compatible. The package command mapping is additive and fixes global installation. Existing unpinned Kennel installations can use `kennel tool update muzzle`; pinned source installations must select v1.1.2 explicitly.

Existing projects should add `state/` to `.muzzle/.gitignore`. Initialization preserves user-owned files, and ignore rules do not untrack committed files. Loop state still requires one writer per project. Workflows run with the caller's permissions; full logs can contain secrets. These established boundaries remain documented.
